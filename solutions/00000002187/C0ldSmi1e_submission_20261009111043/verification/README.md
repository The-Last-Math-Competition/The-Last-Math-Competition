# Evidence index

`engineering-proof/` contains the final public portable verifier result, complete measured inventory, full safe dependency closure, dependency summaries, and actual raw command records. `engineering-controls/` contains the final Python results, all 10 compiled negative controls, strict-sorry rejection, wrong-revision rejection, isolated tracked-mutation control, and all corresponding command records. The actual `result.json` files contain command arguments, working directories, timestamps, exit statuses, stdout, and stderr. Expected fixture audit exits of 1 are successful rejections, not failed candidate proofs.

`compiled-inventory.json` is the expected inventory independently measured from a fresh frozen-source build before the portable run. The public runner reproduces all names, owning modules, declaration kinds, safety, types, direct dependencies, and transitive axioms. `source-manifest.json` binds all 20 verifier inputs, including every mapped author-frozen file. `pinned-dependencies.json` preserves the nine dependency pins and is identical to the packaged Lake manifest.

`author-freeze.json` is the unchanged raw freeze with its actual `conjecture_id` key and 13-file list. `author-original-lakefile.toml` preserves the original configuration, and `author-mathematics.md` preserves the full authored explanation and provenance. `author-logs/` preserves all six original log/verification records byte-for-byte, including the initial failed checking-code build. The final successful author statuses are in `author-logs/verification.json`; the historical failure is not relabeled as success.

`engineering-release-acceptance.json` records the exact current source bindings, frozen-schema adapter, module/path mapping, and explicitly authorized partial control. `engineering-provenance.json`, `generic-scaffold-provenance.json`, and `generic-scaffold-ready.json` identify the engineering reuse and pre-freeze/post-release boundary. No previous mathematical solution, report, proof strategy, inventory, or mathematical evidence is included through that generic tooling reuse.

`partial-control-metadata.json` records the reporting-only inspection of the genuine compiled `partial def` fixture. Its exported public constant is safe and its two compiler execution stages are unsafe. The production audit rejects the first unsafe stage. This accurately records a real partial-source rejection without claiming that the separate `.partial` metadata branch was directly reached. This inspection is not counted as an additional negative fixture.

`independent-core-review.json` is the supplied fresh reviewer's mathematical-core receipt. Its listed scratch proof/audit files remain local; they are not copied or treated as additional premises here. The core receipt explicitly excludes the later package/report review. `independent-report-review.json` separately records complete source and two-page PDF review, with no requested edits; it still leaves the final engineering package for separate review. `root-report-qa.json` is the supplied coordinator's report compilation and visual-inspection receipt. `report.tex` and `report.pdf` were copied exactly. These review roles are separate from this engineering agent's work.

`selected-raw-records.json` maps every included selected final run file to its original absolute path and SHA256. The original output manifests also cover temporary fresh-project files and remain local at `/private/tmp/tlmc2187-engineering/public-01` and `/private/tmp/tlmc2187-engineering/controls-01`. Those full manifests are not presented as package manifests for omitted files. Authored build artifacts, dependency caches, generated bad Lean fixture modules, synthetic Git repositories, and duplicate temporary sources are not packaged. The actual fixture source strings remain reviewable in the control script and result records.

Historical absolute paths describe where the recorded runs occurred; they are not installation requirements. Reproduction uses the packaged inputs and the explicitly supplied runtime/dependency paths. Local checks and review do not imply maintainer acceptance. The coordinator may add final independent package, reproduction, or publication receipts after this engineering stage.
